## DBP37: representative renderer and resource result

DBP37 MAP04 is a real 3,817-linedef map. One warm smoke plus five alternating production A/B pairs exited 0, rendered screenshots, and recorded no new display-driver event. Candidate `pf018stats` on MAP04 reports about 5,695 vertex allocations, 5,719 searches, 5,848 candidate-span inspections, 24 grows, a peak of two free ranges, exclusively the small-list path, zero index mutations and zero invalid allocator operations. Counts are concentrated in level setup: only one allocation occurs between the 120-frame snapshots. AABB update calls occur, but moved-line and path-lookup counts are zero. This map qualifies the allocator/growth and buffer-capacity path, not moving-AABB CPU work; its visual density is not offered as proof of AABB optimization. MAP09 also launched and exited 0 on both revisions, with setup allocation/growth but zero moved lines.

The unmodified production `dumplevelmesh` exports repeated these exact MAP04 allocated element counts in all five pairs: vertices **112,090 baseline / 47,427 candidate**; surfaces **19,682 / 12,138**; index elements in use 83,724 on both. Identical read-only `pf018capacity` commands in isolated diagnostic builds measured all ten main `LevelMesh::Mesh` arrays. Four complete diagnostic pairs (01–03, 05) reported the same vector and logical byte count each time:

| Array elements | Baseline | Candidate |
|---|---:|---:|
| vertices / uniform indices | 112,090 each | 47,427 each |
| indices / surface indices | 213,162 / 71,055 | 88,258 / 29,420 |
| surfaces | 19,682 | 12,138 |
| uniforms / light uniforms / materials | 6,560 each | 8,092 each |
| lights / light indices | 20,000 / 0 | 20,000 / 0 |
| Sum of ten array `Size() × sizeof(element)` | **11,702,876 bytes** | **8,635,124 bytes** |

The reduction is **3,067,752 logical bytes (26.21%)** on this real map. It is attributable to the PF-018 growth/allocation policy on the matched source pair. It is not a claim about actual Vulkan heap residency, container spare capacity, or FPS. Candidate AABB parent/leaf index elements add nominal storage outside these ten arrays; the MAP04 diagnostic tree has 1,707 nodes and 854 lines, or 10,244 nominal cache bytes. That does not erase the measured main-array reduction. Paused, fixed-camera MAP04 world pixels in rows 100–799 are exactly equal. Full OBJ face hashes from free-running captures vary within revisions by two triangles of moving midtexture 1678; those captures are not treated as fixed-tic geometry proof. The targeted fixture below supplies exact moving-path geometry/query evidence.

One early uncapped DBP37 MAP01 launch on the **baseline** stopped at map startup and recorded three new `nvlddmkm` 153 events; the 60-second watchdog ended it without a screenshot. It was not run on the candidate and is not attributed to PF-018. As a control, Doom2-only MAP01 exited 0, captured screenshots and produced no driver events on both revisions under matched capped settings. DBP37 MAP04/MAP09 are the reliable qualified maps on this driver. No DBP50 launch was performed in this campaign; its prior two variants' local crash evidence remains a separate compatibility matter.

One test-only MAP04 candidate capacity run (04) hit the watchdog after its first readout; it coincided with reported mouse movement and logged no driver event. Its cause is not established. It is excluded from all timing/image claims; the runner stopped the batch. A later clean paired diagnostic run (05) exited 0 and reproduced the same capacity vector. The five unmodified production pairs all exited 0. The raw timeout remains preserved.

## Moving AABB and PF equivalence

The original `PF018_PolyAABB.wad` (SHA-256 `deb0359eee42ce2f84ebab9a18f7840a2ca21a41babfee888779292f8f562cef`) has moving polyobjects but no light to activate the shadow AABB update path; both revisions report zero AABB calls/moved lines. The test-only derivative (SHA-256 `61343ae0aa40783e75561b1bb93b01601e7b1f0ddb2d6bce4297752432788545`) adds only a GLDEFS light and preserves every original lump byte. It records nonzero AABB update/moved-line counters.

On isolated diagnostic builds at the exact source SHAs above, all **1,630** fixed-tic renderer-private `LevelAABBTree::RayTest` input/fraction records are byte-identical, including 1,280 moving-line rays. The complete baseline capture is `baseline-query2`; `baseline-query` skipped tic 117 and is excluded. The ray vector SHA-256 is `b90efeb5c9e7d928df2ced3046bca9b1ac1d9fa2fe7ca1c7eb5c1bf6978781cf` on both sides. Five alternating normal-interpolation pairs measured `DoomLevelAABBTree::Update` warm nanoseconds per moved line at **310.378 baseline / 159.175 candidate** median, a **48.72% reduction**; candidate won all five. This is an AABB-subsystem result, not whole-frame speedup. It costs 3,116 nominal parent/leaf index bytes for this 519-node/260-line tree. Test-only patches, binary hashes, raw samples and analysis are retained next to the logs.

The unmodified production binaries ran both original and GLDEFS-light fixtures. At paused checkpoints, rows 32–799 of the world image matched exactly for each fixture, and the oriented face multisets matched exactly at 33,036 faces. The diagnostic query-run screenshots were taken at different moving-scene phases and are not used for image equivalence. On the moving light fixture, a separate one-warmup/five-pair symmetric diagnostic of cumulative `DoomLevelMesh::BeginFrame` time gave 20.129 ms baseline / 20.082 ms candidate median per measured frame (−0.23%, mixed pairs). It supports no material whole-path CPU regression and is not claimed as a material overall speedup. On that stress fixture the candidate uses more vertex slots (78,728 / 88,258) but fewer total bytes across the same ten main arrays (16,083,412 / 15,664,932), before the 3,116 nominal cache bytes; this prevents a selectively reported vertex-only memory claim.

PF-018 leaves dirty upload merging/copy semantics unchanged, so byte-identical upload optimization is not claimed. The PF oracle's compiled LevelMesh fixture covers PF-004 generation/span ownership, wrong-span/double/overlap protection, deterministic best fit, small/indexed transitions, bounded growth with stationary live ranges and 10,000 fragmentation operations. The full deterministic oracle and inherited Windows/macOS/Linux matrix passed on reconciled implementation head `7d390a3` in [Continuous Integration run 36000665523](https://github.com/techrote/ShadeDoomVK/actions/runs/36000665523). The local Windows `python -m unittest discover` invocation ran 102 tests but 11 compiled-fixture cases could not start because the POSIX `c++` executable is absent; the hosted exact-head Linux oracle ran those compiled fixtures and passed. Two local baseline-oracle JSON runs were byte-identical. Final documentation-head CI and post-merge state still require verification before #35 can close.

## Decision boundary

The paired real DBP37 workload demonstrates a substantial LevelMesh resource improvement from PF-018 growth/allocation, while the changed AABB path has direct fixed-tic query equality and a repeatable subsystem CPU gain. PF-004 identity and deterministic stress gates pass, and no measured material regression outweighs the resource gain. This qualifies the runtime acceptance evidence for PR #68. Acceptance is complete only after final-head CI, merge-to-master verification and required post-merge checks; this document must be updated with those exact revisions before #35 closes.
