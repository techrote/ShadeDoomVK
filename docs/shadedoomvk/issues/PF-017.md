# PF-017 — Light/material data deduplication and cache lookup performance

## Objective

Reduce repeated dynamic-light data upload and material descriptor-variant lookup cost without changing selected lights, light ordering/class semantics, texture bindings, sampler choices or rendered output.

## Scope / required work

- Profile `VkRenderState::UploadLights`, `LightBufferSSO` construction/usage and repeated `FDynLightInfo` copies across surfaces/actors after PF-016.
- Design/implement deduplication of physically identical light records where ranges/index lists can reference one uploaded record while preserving normal/subtractive/additive grouping and ordering semantics visible to shaders.
- Preserve exact per-consumer light lists and fall back when identity/lifetime makes dedup unsafe.
- Replace `VkMaterial::GetDescriptorEntry` linear variant scan with an explicit hashed/canonical lookup keyed by the same accepted clamp/translation/global-shader/palette state after PF-013 correctness repairs are accepted.
- Where clearly equivalent, reduce repeated descriptor consumption for default/placeholder material resources without changing shader-visible layer semantics; integrate PF-003 generations.
- Instrument unique-vs-referenced lights, upload bytes, descriptor lookup hit/miss/probe cost and descriptor slots saved.

## Non-goals

- No selected-light culling/reduction.
- No light math/quality change.
- No semantic material feature change or new height maps.
- No descriptor-capacity policy redesign.

## Dependencies

PF-003, PF-008, PF-013, PF-016.

## Concurrency guidance

Do not overlap PF-016 shared light-data refactors or PF-013 material correctness implementation. May overlap PF-018 when files are separate. PF-019 depends on this accepted performance baseline.

## Required context

Read `AGENTS.md`, PF dependencies, `rag/02-RENDERER-IDENTITY-LIFETIME.md`, `rag/04-MATERIAL-SHADER-CONTRACT.md`, lighting RAG, known traps and current light-buffer/material-descriptor source.

## Autonomous implementation prompt

Complete PF-017 autonomously. Measure current duplicate light uploads and descriptor-variant scans, implement canonical dedup/lookups preserving exact semantic lists/bindings, run side-by-side state/image equivalence and measured performance, then branch→PR→checks→merge→verify `master`→RAG/ledger→close.

## Acceptance criteria

- Each consumer sees the same logical ordered light set/classes as before.
- Qualified repeated light records consume less upload/buffer work, with measured improvement on a representative light-rich workload.
- Material descriptor lookup returns the same bindless range for the same accepted post-PF-013 state and distinguishes all previously distinct variants.
- Any default-resource descriptor saving is generation-safe and shader-semantically identical.
- No image/state quality change in PF equivalence fixtures.
- Required CI passes; PR merged and verified.

## Verification

Compare pre/post per-consumer light lists and shader ranges, duplicate/unique counts/upload bytes, material variant keys/results across translations/clamps/global shaders/palette modes, PF-013 regression fixtures, descriptor reuse/reset stress and image/state evidence.

## Expected artifacts

Light-data dedup representation; hashed material variant lookup; optional equivalent default-resource sharing; benchmarks/tests/diagnostics; RAG/ledger updates.

## Blocking / stopping conditions

Stop deduplication if light record identity cannot be proven stable for the required lifetime/order semantics. Stop hash conversion if any previously distinct descriptor state collides or if PF-013 material correctness is not accepted. Prefer retaining a measured slower path over semantic aliasing.

## Profiling decision (2026-09-24)

Accepted master baseline 66b09a872b9d45b496a27c1bf1406d8a74606cd2 was measured on the physical GTX 1650 SUPER before an optimization was selected. A dense PF-016 frame had 49,473 logical light references, 217 distinct packed records and 3,971,280 mapped copy bytes. A frame-local per-record hash/indirection prototype reduced writes 94.24% but worsened representative production S: Setup from 3.615 to 8.432 ms median across five alternating pairs (+133.25%); every pair regressed. Five full images matched exactly. The prototype was restored, not merged. Material caches held at most one variant in the dense scene and three in DBP37 MAP04, so hashed lookup has no demonstrated benefit. No default-resource sharing was attempted.

PF-017 is **not accepted**. Issue #34 remains open, and PF-019 remains blocked. Exact SHA/binary hashes, commands, state limits, raw local artifacts and next concrete action are in [PF-017-PROFILING-NOTES.md](../PF-017-PROFILING-NOTES.md). This negative evidence does not weaken any acceptance criterion.

## Second attempt: source-owned reuse and real material variants (2026-09-24)

Current accepted master b5fcab0a4c4847607007a6562c74b28c6e46a4d3 is renderer-identical to the first baseline. A source-owned packing-revision/temporal-write prototype avoids per-reference hashing and shader indirection: five alternating physical-GPU pairs improve S: Setup 3.660 -> 3.410 ms (-6.83%), all five images exact, with 13.83% fewer mapped bytes. Dense and moving-fixture checkpoint buffers match; direct packing-oracle mismatches are zero. It retains the full physical record layout and has not completed source-ID/lifetime/adversarial acceptance.

Published Champions content raises material populations to 15 variants (17 with its all-champions setting), but node and flat canonical indexes regress versus the same executable's accepted linear oracle by 94.8% and 36.8%. All observed lookup results match. Experimental renderer changes were restored. This subset does not fulfill the full scope; **PF-017 remains not accepted, #34 open and PF-019 blocked**. [PF-017-REUSE-RESEARCH.md](../PF-017-REUSE-RESEARCH.md) contains exact base/patch/binary identities, commands, pairs, machine-readable analyses and next action. A documentation/evidence PR is not implementation acceptance.

## Material-only workload qualification (2026-09-24)

On master `84bbbacbc2cea8568e78ac2f0e059ffc5608a897`, Sunlust MAP30 with published Champions and checksum-verified Freedoom sustains median 1,201 >8-entry lookups/frame in an authored arena. Estimated large-population search is only 47.13 microseconds/frame; misses dominate attributed material cost. A previous-hit shortcut would increase expensive-population comparisons 1.81%. A later MAP24 arena timed out with NVIDIA error 153, stopping production confirmation and the paired campaign. No lookup candidate was implemented or retained; all probes were restored. This is a **no-go for implementation on current evidence**, not proof that every optimization is slower.
