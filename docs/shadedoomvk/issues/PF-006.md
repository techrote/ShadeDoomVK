# PF-006 — Typed shader/pipeline keys and cache contract

## Objective

Replace pipeline/shader/render-pass identity based on whole-object `memcmp`/padding assumptions with explicit canonical key semantics while preserving exactly which renderer states map to distinct pipelines/shaders.

## Scope / required work

- Audit `VkPipelineKey`, `VkRenderPassKey`, `VkShaderKey`, their construction sites, generalized/specialized shader paths and pipeline cache/library lookups.
- Define explicit equality/hash/order or canonical packed serialization from meaningful fields only.
- Build a temporary old-key→new-key comparison diagnostic over PF fixtures to prove one-to-one state partitioning before removing object-representation dependence.
- Preserve pipeline libraries, disk Vulkan pipeline cache, generalized/specialized behavior, background/precache compilation and user-shader distinctions.
- Use hash lookup where appropriate only after identity correctness is proven; record performance separately from correctness.
- Remove obsolete padding fields/static asserts whose only purpose was `memcmp` stability when safely possible.

## Non-goals

- No shader lighting/material behavior change.
- No new shader permutations for later POM/shadow features.
- No broad pipeline worker rewrite; PF-019 may optimize after the key contract is stable.

## Autonomous implementation prompt

Complete PF-006 autonomously. Instrument the old identity first, introduce typed canonical keys, prove old/new equivalence across PF fixtures and pipeline creation cases, preserve compilation/cache behavior, and only then remove representation-dependent comparison. Dedicated branch → tests/docs → PR → checks → merge → verify `master` → update RAG/ledger → close on acceptance.

## Acceptance criteria

- Key equality/hash/order depends only on explicitly named renderer state.
- PF fixtures show no unintended old-key split/merge under the new keys.
- Pipeline/shader output/state remains equivalent.
- User shaders, generalized/specialized paths, pipeline libraries and cache loading continue to function.
- Any lookup-performance claim has measurement; correctness does not depend on the speedup.
- Required CI passes; PR merged and verified.

## Verification

Record old/new key pairs over representative materials, blend/depth/stencil/cull modes, ray/shadow modes, user shaders, LevelMesh and postprocess-adjacent paths; assert one-to-one mapping; run PF image/state equivalence and pipeline-cache warm/cold tests.

## Expected artifacts

Typed key implementation; equivalence diagnostic/tests; updated Vulkan RAG; evidence/ledger entry.

## Blocking / stopping conditions

Stop if two semantically distinct old states map to one proposed key, if old object padding contains hidden state not understood, or if cache serialization compatibility cannot be handled safely. Preserve old keys until the ambiguity is resolved.

## PF-006 implementation contract

The implementation contract is recorded in `docs/shadedoomvk/PF-006-PIPELINE-KEY-CONTRACT.md`.

PF-006 keeps the packed `VkShaderKey::AsQWORD` specialization ABI while moving C++ cache equality/order for the three assigned keys to explicit semantic state. The generalized shader cache retains its inherited narrower partition, the graphics-pipeline library and worker/precache routes remain structurally unchanged, and the on-disk Vulkan driver pipeline cache remains an opaque driver blob rather than renderer-key serialization.

Acceptance remains pending until the implementation PR and required CI matrix pass, the merge is verified on `master`, programme-level evidence is reconciled in the execution ledger, and issue #23 is explicitly closed.
