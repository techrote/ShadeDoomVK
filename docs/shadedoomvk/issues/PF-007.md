# PF-007 — Central Vulkan capability and driver-quirk registry

## Objective

Centralize Vulkan feature/limit/vendor/driver capability knowledge behind explicit queries/data while preserving the baseline's effective fallbacks and workarounds.

## Scope / required work

- Inventory capability/limit/vendor/driver checks in Vulkan renderer code, especially sampler Intel device/driver policy, ray-query/AS support, descriptor indexing/limits, pipeline-library use, sample counts, clip/depth/normal-format decisions and related fallbacks.
- Introduce a renderer capability/quirk structure/service populated once from physical-device/driver data.
- Replace scattered duplicate policy checks with named queries where safe.
- Preserve existing workaround behavior first; record provenance/reason for vendor/driver overrides.
- Expose diagnostic capability/quirk state for PF/SDVK verification.
- Define separation between descriptive hardware capability and later user-facing quality-tier policy.

## Non-goals

- Do not remove/retune Intel or other workarounds merely because they look old.
- Do not change quality defaults or require optional Vulkan features.
- Do not implement SDVK-016 tier selection.

## Dependencies

PF-001.

## Concurrency guidance

May overlap PF-002/PF-004/PF-006/PF-009/PF-011. PF-010 and PF-019 depend on it. Coordinate with PF-006 if capability bits participate in shader/pipeline key construction.

## Required context

Read `AGENTS.md`, PF-001 evidence, `rag/08-VULKAN-PIPELINE-CAPABILITIES.md`, current Vulkan device/sampler/renderbuffer/pipeline code and canonical body.

## Autonomous implementation prompt

Complete PF-007 autonomously. Inventory current checks and effective behavior, introduce a central descriptive capability/quirk registry, migrate checks incrementally with equivalence fixtures, preserve all established fallback/workaround semantics, add diagnostics, PR/check/merge/verify, and update RAG/ledger.

## Acceptance criteria

- Named capability/quirk state covers the audited feature/limit categories.
- Migrated paths produce the same decisions on PF fixture/mock/device-capability cases as baseline.
- Existing vendor/driver workarounds retain documented reasons/provenance.
- Optional ray-query/AS/pipeline-library paths still have explicit fallbacks.
- No visual/quality policy change.
- Required CI passes; PR merged and verified.

## Verification

Use unit/mocked capability cases where feasible plus real runtime diagnostics; compare old/new sampler/filter decision logic for representative Intel/current/legacy/non-Intel cases; verify ray-query-disabled and descriptor-limit paths; PF image/state equivalence.

## Expected artifacts

Capability/quirk registry; migrated queries; diagnostic dump; tests; updated Vulkan RAG/evidence/ledger.

## Blocking / stopping conditions

Stop if a workaround's intent/effective condition cannot be reconstructed or a migration would alter behavior without validation. Leave that check local and document it rather than deleting it speculatively.
