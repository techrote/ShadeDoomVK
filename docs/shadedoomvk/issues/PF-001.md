# PF-001 — Pre-foundation renderer safety harness and invariant fixtures

## Objective

Create the smallest trustworthy regression/diagnostic oracle required to execute PF-002..PF-019 without relying on subjective screenshots or code-shape assumptions.

## Scope / required work

- Inspect current `master`, inherited CI/build paths and renderer diagnostics before changing behavior.
- Add a compact deterministic PF fixture set covering the pre-foundation contracts: resource allocate/free/reuse, representative material variants, actor dynamic-light selection, portal-relative lighting, probe/lightmap state, sprite clipping/orientation state, shadow-light cap/selection state and relevant main/portal/camera/probe render contexts.
- Preserve minimized failing fixtures for confirmed baseline defects where they can be reproduced before their owning PF issue.
- Add machine-readable/debug diagnostics sufficient for later PF issues to compare selected light/probe/shadow/resource/pipeline state and key allocation counters.
- Define the PF image/state equivalence procedure and baseline captures/hashes/tolerances used by refactor/performance issues.
- Keep fixtures small enough for repeatable local/CI smoke execution.

## Non-goals

- Do not perform ShadeDoomVK rebranding/build-policy work owned by SDVK-001.
- Do not build the complete durable reference/benchmark corpus owned by SDVK-002.
- Do not fix PF-012..PF-015 defects in this issue unless a minimal harness change cannot otherwise run; record such a blocker instead.
- Do not add headline visual features.

## Dependencies

None. This is the root PF gate.

## Concurrency guidance

Complete PF-001 before starting implementation of other PF issues. Planning/document-only work may overlap, but PF implementation must consume the accepted oracle.

## Autonomous implementation prompt

Complete PF-001 autonomously in `techrote/ShadeDoomVK`. Inspect current `master`, CI and relevant renderer/source history first. Establish deterministic pre-foundation fixtures and machine-readable diagnostics without intentionally changing accepted rendering. Work on a dedicated branch, add tests/docs/evidence, open a PR, repair every required automated check attributable to the change, merge only after required checks pass, verify the merge on `master`, update affected RAG/ledger material, and close only when the acceptance criteria genuinely hold.

## Acceptance criteria

- A documented command/workflow executes the PF smoke fixture set reproducibly enough to compare refactors.
- The harness exposes state needed to falsify stale resource identity, wrong light/probe/shadow selection and key view/portal mistakes.
- Baseline captures exist for the PF equivalence contract.
- Confirmed baseline defects assigned to later PF issues are represented by minimized reproducers where practicable, or a precise reason is recorded when a reproducer cannot yet be automated.
- No deliberate visual/quality policy change is introduced.
- Required CI passes; PR is merged and verified on `master`.

## Verification

- Run the PF fixture command at least twice from clean/restarted state and compare machine-readable output stability.
- Exercise at least one positive and one negative/edge fixture for resource lifetime, lighting/occlusion, probe/lightmap and portal/view context.
- Record current expected failing fixtures separately from passing invariants so later bugfixes can change only the intended expectations.

## Expected artifacts

- PF fixture/test assets or generated deterministic fixture definitions;
- machine-readable/debug diagnostic output path;
- baseline evidence manifest;
- concise developer instructions for running the PF oracle;
- updated RAG/ledger if discovered source truth differs from planning.

## Blocking / stopping conditions

Stop and record a blocker rather than weakening criteria if the inherited build/CI cannot produce a trustworthy baseline, if fixtures cannot distinguish materially different renderer state, or if a supposed diagnostic change itself materially alters the rendering path being measured.
