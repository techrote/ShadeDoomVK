# PF-010 — Render-view/pass context extraction

## Objective

Make main-view, portal/mirror, camera-texture, light-probe cubemap and special/experimental scene renders explicitly distinguishable renderer contexts so persistent caches and future temporal features cannot accidentally share incompatible state.

## Scope / required work

- Audit `RenderView`, `RenderViewpoint`, `HWDrawInfo`, portal scene state, camera-texture rendering, probe cubemap rendering and Vulkan scene entry paths.
- Introduce a lightweight render-view/pass context with explicit type, stable-within-pass identity/epoch, parent/recursion information where relevant, portal/mirror state and flags for main/postprocess/history eligibility.
- Thread/access that context at key renderer cache/diagnostic boundaries without globally plumbing unnecessary state through unrelated gameplay code.
- Preserve all current view transforms, portal recursion, camera texture and probe rendering behavior.
- Add diagnostics/fixtures proving distinct context identity for main, mirror/linked portal, camera texture and probe faces.
- Document future history-invalidation seam but do not implement temporal history.

## Non-goals

- No TAA, motion vectors, temporal volumetrics or SSR history.
- No portal semantic redesign.
- No user-facing rendering mode changes.
- Do not fix PF-014/PF-015 correctness bugs unless a context extraction supersedes their failing path; preserve reproducers if so.

## Acceptance criteria

- Main, portal/mirror, camera texture and probe-render paths expose distinct inspectable context identities/types.
- Recursive portal parent/handedness information required by renderer caches is preserved.
- Existing render output/transforms remain equivalent.
- No temporal feature/history is added.
- Context can be used by later visibility/probe/temporal work without relying on global main-view assumptions.
- Required CI passes; PR merged and verified.
