# PF-019 — Pipeline/resource micro-performance and dormant-path cleanup

Status: **accepted**. Implementation PR #107 head `e496977a47ebb7a4235dba28a7df11128780b0eb` passed all 8 required jobs in CI run `37108111799`, merged as `44864d9d27495d3992d3a7314f4cb7de6c029b7b`, and all 8 post-merge jobs passed on that exact merge in run `37108571879`.

## Objective

Harvest remaining low-risk renderer overhead after the major PF refactors: improve canonical pipeline/cache lookup, avoid work/resources belonging solely to provably dormant paths, and accept shader/worker micro-optimizations only when measured and output-equivalent.

## Scope / required work

- Measure pipeline/shader/render-pass lookup and compilation scheduling after PF-006; use canonical typed hashes/maps where they materially reduce lookup cost without changing cache identity.
- Audit creation/use of Z-min/max/light-tile resources and associated descriptors/pipelines. Where the tiled-light path is disabled/dormant, conditionally avoid allocations/dispatch preparation that have no active consumer, while preserving easy re-enable/research seams for SDVK-009.
- Audit render/resource begin-frame work for other clearly unused dormant allocations introduced by inherited experimental paths; require proof of no active consumer before gating them.
- Inspect generated SPIR-V/compiler output before hand-changing repeated dynamic-light vector/distance calculations; accept source micro-optimization only if generated code/performance improves and output remains equivalent.
- Review pipeline/texture worker queue overhead for small measured improvements that do not change ordering/lifetime semantics.
- Record every adopted/rejected micro-optimization with measurement so future agents do not repeatedly rediscover compiler-neutral ideas.

## Non-goals

- No visible quality reduction, resolution/precision/filter changes or light-count reduction.
- No activation/redesign of tiled/clustered lighting; SDVK-009 owns architectural research.
- No broad render-graph rewrite.
- No speculative source golfing without measured generated-code/runtime benefit.

## Candidate disposition

The measured retained change is deliberately narrow: gate the inherited tiled-light producer resources while the accepted renderer has no consumer. `VkLightTilePolicy::Enabled` is the single re-enable seam. While false, the renderer skips Z-min/max images, Z-min/max/light-tile descriptor resources and per-frame rewrites, the five dedicated shader compilations, and the four dedicated pipelines. LevelMesh descriptor binding 4 remains unchanged and receives one valid `LightTileBlock` storage allocation so descriptor ABI and future re-enable work do not depend on a null binding.

At the PF-017 representative 1904x1001 output, the inherited formulas require 5,241,600 bytes of six-level RG32F Z-min/max texels plus 622,080 bytes of tiled-light storage. The candidate retains one 1,296-byte binding block and therefore avoids 5,862,384 bytes before Vulkan allocator overhead on that screen render buffer. This is a deterministic allocation/work result, not a frame-time or VRAM-residency claim.

Rejected/omitted candidates:

- PF-006 `std::map` pipeline/shader/render-pass topology remains unchanged. No representative workload demonstrated that a typed hash structure would repay its own hashing/allocation/cache costs, so PF-019 does not substitute one speculatively.
- no shader-source arithmetic change is made; generated-code qualification is therefore not invoked for a nonexistent candidate;
- worker priority/precache/main-thread queue ordering remains unchanged because no measured scheduling win justified touching lifetime/order semantics;
- no additional renderer resource is gated where consumer status was ambiguous.

See `PF-019-PERFORMANCE-REVIEW.md` and `test_pf019_dormant_resources.py`.
