# PF-011 — Lighting math, units and compatibility-bridge contract

## Objective

Centralize and name the inherited renderer's dynamic/PBR/sun/classic-light mathematics and compatibility constants so later lighting work has an explicit contract instead of scattered magic factors, while preserving accepted baseline output.

## Scope / required work

- Audit CPU/GPU attenuation, light strength/intensity, additive/subtractive treatment, `PBRBrightnessScale`, ambient-sector-light approximation, sunlight representation, fake model light and relevant GLDEFS properties.
- Document the current conceptual units/normalizations even where they are compatibility constructs rather than physical photometric units.
- Move duplicated equations/constants into shared/named functions/constants where doing so preserves output and shader/compiler behavior.
- Make the classic-light → PBR compatibility bridge explicit in diagnostics/docs.
- Add equation/vector fixtures comparing CPU and shader-side expected values for representative distances/radii/linearity/spot angles/colors.
- Preserve current light-authoring semantics and visible response; calibration/retuning is future work.

## Non-goals

- Do not introduce physical lumen/lux units or retune existing maps/mods.
- Do not redesign probe IBL, shadowing or light selection.
- Do not change user-facing light defaults or quality tiers.
- Do not implement bloom/exposure policy.

## Implementation contract

PF-011 is implemented around `docs/shadedoomvk/PF-011-LIGHTING-COMPATIBILITY-CONTRACT.md` and a deliberately narrow compatibility bridge:

- CPU dynamic-light list packing owns named additive/color/linearity/sun-proxy constants/helpers in `hw_lightcompat.h`.
- shader-side sunlight/PBR bridge values are named in `lightmodel_shared.glsl` and consumed by PBR/specular paths without numerical retuning;
- the inherited distance-attenuation operation ordering remains unchanged;
- the CPU aggregate sprite-light path remains separate because its minimum inverse-square distance, raw linearity input and additive behavior are not semantically identical to GPU list packing;
- adversarial numerical/source fixtures live in `tools/pf_oracle/tests/lighting_compat_fixture.cpp` and `test_lighting_compat_contract.py`.

This section records implementation ownership only. Acceptance still requires exact-head CI, merge, verified `master`, RAG/ledger reconciliation and issue closure.

## Acceptance criteria

- Current attenuation/intensity/PBR/sun/ambient compatibility math has named documented ownership.
- Representative CPU/shader reference vectors match baseline within declared numerical tolerance.
- Existing GLDEFS/light-authoring response and PF images remain equivalent.
- No physical-calibration or quality-policy change is smuggled into the refactor.
- Future lighting code can reference a clear compatibility bridge rather than hard-coded scattered constants.
- Required CI passes; PR merged and verified.

## Verification

Numerical tests for linear/inverse-square blend, spot attenuation, additive/subtractive color, sunlight and PBR scaling; PF moving-light images/state; representative legacy/PBR material comparison.

## Expected artifacts

Named math/constants/helpers; numerical fixtures; lighting-contract documentation/diagnostics; updated lighting/HDR RAG; evidence/ledger entry.

## Blocking / stopping conditions

Stop if duplicated-looking equations are not semantically equivalent or compiler/shader movement changes accepted output beyond tolerance. Document separate compatibility paths instead of forcing artificial unification.
