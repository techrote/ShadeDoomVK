# PF-016 — Unified dynamic-light query service and exact-equivalence actor fast path

## Objective

Reduce CPU dynamic-light collection cost by consolidating candidate/filter/portal/visibility logic, replacing sorted duplicate insertion with O(1)-style generation marking, and implementing a qualified section-local actor fast path only where it produces the exact same selected lights as the accepted baseline semantics.

## Scope / required work

- On top of PF-009/PF-011/PF-015, inventory current light collection for sprites/models and adjacent reusable logic for walls/flats/decals without forcing unsuitable consumers into one abstraction.
- Introduce a shared light-query service or compact functions for portal-relative position, eligibility/filtering, distance/radius tests and visibility-cache invocation.
- Replace per-query `SortedFind`/sorted insertion duplicate suppression with generation-stamped/indexed O(1)-style membership where stable light identity permits it.
- Adapt/reimplement the useful concept from `MAD-VKDoom@2c433f2a495ec208c6cc9e248c2c85e3bb14a6f5`: for a precisely defined actor/section/portal predicate, source candidates locally instead of BSP walking.
- During qualification, run the accepted baseline and only persist the local shortcut when the touched-section/portal predicate proves that both sources are the same section light list in the same order.
- Preserve PF-015 world/view cache validity and portal-group displacement semantics.
- Add candidate/visited-section/duplicate/filter/trace timings and counts.

## Implemented repair

The implementation branch introduces `HWGenerationSet<FDynamicLight*>` on `HWDrawContext`. Every actor/model collection advances a generation and uses `MarkFirst(light)` for first-encounter membership, eliminating the old `addedLights.SortedFind` plus sorted insertion maintenance while preserving traversal/output order.

`HWDrawInfo::GetDynSpriteLightList` now has one `processLightList` pipeline shared by both candidate sources. It retains `ShouldLightActor`, `PosRelative(group)`, radius/render-radius overlap, PF-015 visibility tracing/cache validity, and `AddLightToList` classification unchanged.

The local path is intentionally narrow. A baseline `BSPWalkCircle` qualifies the actor's exact current query state only when every touched subsector resolves to the actor's own section and portal group. The result is cached with query position, render radius, section and portal group; any key change falls back to baseline qualification. Empty, multi-section and cross-portal-group cases remain baseline. This gives repeated static actors in section interiors a direct `section->lighthead` source without importing donor portal assumptions.

`stat actorlightquery` records baseline/local query counts, visited lists, candidates, duplicates, filters, traces and baseline/local nanoseconds. The compiled adversarial fixture verifies first-encounter identity/order, generation reset, local qualification boundaries and dense duplicate equivalence, and emits a dense sorted-vs-generation timing sample without making CI correctness depend on noisy wall-clock thresholds.

The detailed contract and independent provenance boundary are in `docs/shadedoomvk/PF-016-LIGHT-QUERY-CONTRACT.md`.

## Acceptance criteria

- One documented query path owns actor candidate eligibility/portal-relative/filter/visibility semantics without changing the selected set.
- Duplicate suppression no longer requires maintaining a sorted per-query light list in the qualified path.
- Fast-path and baseline selected light identities/classes/order are equivalent for its declared predicate, including portal fixtures.
- Unsupported/ambiguous cases fall back to the baseline-correct path.
- At least one representative dense-sprite/light workload shows measured CPU improvement with equivalent image/state.
- Required CI passes; PR merged and verified.
