## Observed failure and correlation

One launch was made. The game reached MAP01 - Glass Messiah. At frame 7, tic 5, graphics submissions 10 and 11 both returned VK_SUCCESS from vkQueueSubmit. Image acquisition and vkQueuePresentKHR also returned success. The next frame-fence wait entered at 15:55:45.913 UTC and returned VK_ERROR_DEVICE_LOST 1.903 seconds later, at 15:55:47.816 UTC; the application reported Could not wait for commands. The returned wait is the first application-observed failure, not proof that the wait or submission 11 caused it.

New System records 5055 and 5056 are nvlddmkm event 153 at 15:55:45.9163465 and 15:55:47.7842744 UTC. Both report Video3 / GPUID 700. Their XML was exported beside the plan. No new WER 141 record or matching new WATCHDOG live dump was found on the delayed offline recheck; do not classify this attempt as a separately proved Windows 0x141 live dump. A 60-second runner timeout followed because the fatal-error dialog stayed open.

The GPU checkpoint query after device loss returned graphics TOP_OF_PIPE marker 0000020048BFE080 and BOTTOM_OF_PIPE marker 0000020048BFF3C0. Both map to command buffer 000001FF923BE0D0 in graphics submission 10. The latter was recorded at the world stage in frame 7; the startup marker is a nested stage-scope exit and does not imply that map startup ran after world. These are GPU-executed markers, distinct from CPU stage logs. Their stage semantics do not isolate a faulting instruction or exclude in-flight work from submission 11. CPU logging had entered present when it observed device loss at the fence wait; the stage-complete record was emitted afterward during unwinding.

EXT device fault collection succeeded before teardown. It reported type 6 (instruction pointer fault), address 0x200107290 with 16-byte precision, and type 1 (invalid read), address 0x1da00000 with 4096-byte precision. The vendor binary is 488324 bytes and preserved as device-fault.bin. No mapping from either address to a shader, pipeline, descriptor or buffer is established. The run trace recorded 22 pipeline first-use events and 150 shader cache hits, but neither identifies the faulting draw from the available markers.

The pre-kill full process dump is 738640578 bytes. cdb with the matching PDB opened it and wrote threads.txt. Its main thread was in Win32DisplayWindow::RunLoop -> ErrorWindow::ExecModal -> ShowFatalError -> GameMain catch. This is post-error UI state at the 60-second watchdog, not a frozen vkWaitForFences stack. The wait returned in 1.903 seconds. The process dump still proves why the watchdog had to kill the process and avoids mislabeling the timeout as a never-returning Vulkan call.
